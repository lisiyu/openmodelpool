## 本次唯一处理项：P5-3

### 评估结论：缝隙不在"CI 跑得少"，在"CI 声称的分层不存在"

BACKLOG 原文的判断是"CI 硬门禁跑 `-race -short`，README 让贡献者跑全量，P5-1 的 flaky 藏在这条缝里"。实际核查后，结论要更难看一点：

| 核查项 | 结果 |
|--------|------|
| `grep testing.Short()` 全仓 | **0 命中** |
| `grep '^//go:build'` 全仓 | **0 命中**（连一个 build tag 都没有） |
| `grep OMP_TEST_INTEGRATION` 全仓 Go 代码 | **0 命中**（CI 里设了这个环境变量，没有任何代码读它） |

也就是说：

1. 硬门禁那个 `-short` **一个用例都没排除**，它带来的不是"跑得少"，而是"让人以为有一层没跑"。
2. `test-integration` job 与 `test-unit` job 跑的是**完全相同的用例集合**，差别只有 Chrome 预装、超时时长和覆盖率产物。
3. ci.yml 注释里那句 `Runs only short tests (excludes integration tests tagged with //go:build integration)` 是**虚构的**——仓库里没有任何 `//go:build integration` 文件。

这恰好踩中本项目自己的红线：文档（含注释）不得与代码背离。所以本次不是"给 CI 加一轮全量"，而是**把假分层拆掉**。

### 改动

**`.github/workflows/ci.yml`**

- 硬门禁（job id `test-unit`）：`go test -race -short -coverprofile=...` → `go test -race -count=1 -timeout 25m -coverprofile=... ./...`
  - 去掉 no-op 的 `-short`：它排除不了任何东西，留着只会暗示一个不存在的层级。
  - 加 `-count=1`：关闭测试结果缓存。缓存命中的 PASS 是在为**上一次**运行背书，而 flaky 恰好最喜欢躲在缓存后面——这是 P5-1 那类问题的第二条藏身缝。
  - 显式 `-timeout 25m`（`-race` 下全量比本地慢数倍，避免撞上 per-package 默认 10m）。
- 软门禁（job id `test-integration`）：不再伪装成另一个测试层级，改为**独立的第二轮完整复跑**，并把定位写进注释：
  - 抓 flaky。1/3 概率失败的用例，单跑一轮有 2/3 概率放过；跑两轮能显著提高"在贡献者踩到之前先被 CI 抓住"的概率。P5-1 当时正是连跑三轮才复现的。
  - 保留 Chrome 预装：今天 `browser_login_test.go` 只校验 allocator options、不启动浏览器，但将来真用上 chromedp 时，这个 job 保证它是显式失败而不是静默跳过。
  - 删掉无人消费的 `OMP_TEST_INTEGRATION=1`。若将来确有需要外部服务的用例，走 build tag 并在此 job 打开，而不是恢复一个空转的环境变量。

**`CONTRIBUTING.md`** — 测试段落改为："CI 跑的就是你本地那套，只多 `-race` 和 `-count=1`；不存在短/全分层，没有任何东西对你隐藏；另有一轮相同的复跑作为软门禁，专门抓 flaky，允许失败。"

**`README.md`** — 贡献段补一句 `CI gates on the same suite (with -race), so a green local run means a green CI run.`

**`docs/LAUNCH-KIT.md`** — 发布前检查清单补一条：CI 与本地口径已对齐，对外可以说"CI 跑的就是你本地那套"。

### 刻意保留的两处

- **两个 job 的显示名不变**（`Unit tests (with coverage)` / `Integration tests`）。GitHub 分支保护的 required status check 按**显示名**匹配，改名会让已配置的 required check 永久停在 pending，把所有 PR 卡死。这个风险不值得为一个更贴切的名字去冒。
  - **待雷工确认**：若仓库设置里并未把这两个名字设为 required check，可把后者改名为 `Second run (flaky watch)`，名实就完全一致了。
- **CI 触发分支仍是 `[main, master, workbody]`**，`feature/mvp-iteration` 的 push 不触发 CI。这属于触发范围问题、不属于 P5-3 的口径问题，按"不改本次不处理的项"未动。
